## 4. T45-02 — Forced `BayesianEnhancer` exception

Raw evidence: `T45-02-forced-bayes-failure.json`, `T45-02-wire-failed.json`,
`T45-02-wire-healthy.json`.

### 4.1 Platform behaviour — does NOT represent the failure correctly

`ReasonerService.performInference` catches the exception internally (the catch is
commented "Return partial result with error handling"), so `InferenceController`'s own
catch never fires and the platform returns **HTTP 200**. The exact wire payload:

```json
{
  "success" : true,
  "message" : "Inference completed successfully",
  "data" : {
    "patientId" : "mob-3f9c1e84-77a2-4b16-9d05-2ce8a1b47f30",
    "deterministic" : { "molecularSubtype": null, "riskLevel": null,
                        "treatments": null, "biomarkers": null, "reasoningMode": null },
    "bayesian" : { "confidence": 0.0, "posterior": {},
                   "uncertaintyBounds": [0.0, 0.0], "enabled": false },
    "reasoning" : null,
    "riskLevel" : null,
    "dataCompleteness" : null,
    "reasoningMode" : "OPENLLET_SWRL",
    "molecularSubtype" : null
  },
  "apiVersion" : "2.0"
}
```

| Observation | Result |
|---|---|
| Exception propagated to caller | **No** — swallowed |
| HTTP status | **200 OK** |
| `success` flag | **`true`** |
| `message` | **"Inference completed successfully"** |
| Clinical output retained or invented | **No** — subtype, risk, treatments, biomarkers, reasoning, dataCompleteness all `null` |
| `reasoningMode` after failure | **`OPENLLET_SWRL` — stale and misleading** |
| `bayesian.enabled` after failure | `false` — **indistinguishable from a legitimate Bayes-OFF run** |

**Finding — PLATFORM DOES NOT FAIL CORRECTLY.** No clinical value is invented, which is
the critical safety property. But the response asserts success, carries no error
signal, and retains a `reasoningMode` claiming live Openllet reasoning for an inference
that did not complete. Any consumer trusting `success`/`reasoningMode` without
validating the payload body would misread a failure as a live result.

### 4.2 Gateway behaviour — FAILS CLOSED (verified)

The exact serialised payloads above were driven through the gateway's real guard
(`gateway/src/upstream-validator.js` → `validatePlatformSuccess`):

```
--- HEALTHY platform response (T45-02-wire-healthy.json)
    ACCEPTED by gateway    resultMode: LIVE_REASONER
--- BAYES-FAILURE platform response (T45-02-wire-failed.json)
    REJECTED — FAIL CLOSED
    code=INVALID_UPSTREAM_RESPONSE  http=502  outcome=FAILED
    message="The reasoner returned an invalid success response (deterministic result)."
```

**T45-02 conclusion:** the gateway path **fails closed**. A `BayesianEnhancer`
exception cannot deliver partial or invented clinical output to the phone — the
guard rejects the payload at the `deterministic result` check before any mapping,
and returns a `FAILED` outcome rather than a degraded result. The platform's own
failure representation is nonetheless defective and is recorded below.

### 4.3 Observations arising

- **OBS-6 — platform reports success on failure.** `success: true` +
  "Inference completed successfully" + HTTP 200 for a failed inference. The gateway
  compensates, but the platform contract is untruthful. Platform-side remediation is
  **out of scope for Build 45** (canonical checkout is read-only; cf. T45-03 treatment)
  — recorded for the platform backlog.
- **OBS-7 — stale `reasoningMode` survives the failure.** Set at STEP 2, never cleared
  by the catch block. Directly contradicts truthful-delivery labelling.
- **OBS-8 — gateway rejection is incidental, not intentional.** The guard rejects on
  `deterministic result` (null subtype), not on an explicit failure signal, because the
  platform sends none. The fail-closed outcome is correct but rests on payload-shape
  validation. Recommend Gate 7/Gate 10 add an explicit assertion that a `null`
  `deterministic.molecularSubtype` with a non-null `reasoningMode` is treated as
  `FAILED` by contract, so the behaviour is guaranteed rather than emergent.
